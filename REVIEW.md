# Ревью проекта «Игротека» (мульти-модельное)

**Дата:** 2026-09-07
**Статус репозитория:** код полностью локальный (51 файл, коммит `810aebe`). Публичный репозиторий `github.com/timoshinoleg-eng/hub` создан, но **пуст** — пуш заблокирован отсутствием PAT. Ревью проведено по локальному коду; этот файл будет запушен вместе с проектом.
**Кто ревьюил:** 3 независимые модели, разными «линзами»:
- **reasoning** — архитектура и качество кода;
- **default** — безопасность, приватность, 152-ФЗ;
- **lite** — UX и поиск быстрых улучшений из других проектов (с веб-исследованием).

---

## 0. Краткий вердикт

Архитектура необычно дисциплинированна для greenfield: чистые границы модулей, осознанный no-build, реальная забота о 152-ФЗ, настоящий офлайн-тест-харнесс. **Но до публичного запуска есть блокеры** — это прежде всего вопросы реализации, а не дизайна:

1. **152-ФЗ нарушен в аналитике**: `user_id` уходит в сыром виде и *до* согласия.
2. **Неавторизованный `/forget`** и **fail-open админ** (`/cast`, `/stats` открыты всем при пустом `ADMIN_IDS`).
3. **Два бага, ломающих рантайм**: бесконечный цикл `ready↔cfg` в мосту iframe и молчаливый дроп аналитики (неверный Content-Type).

Остальное — поддерживаемость, харденинг и полировка UX.

## 1. Архитектура и качество кода

### Сильные стороны
- Чистое разделение: `games.js` — единственный источник метаданных; `bridge/track/share/duel` — одноцелевые браузерные модули; `server/*` и `bot/*` — бэкенд, общий слой `db.mjs`.
- No-build сохранён: ES-модули грузятся напрямую, `_boot.js` — один общий файл; игры остаются «тупыми» потребителями `cfg`.
- Офлайн-харнесс реально хорош: `app.inject()` (Fastify), реальные `Context`/`Keyboard` бота, `vm`-песочница игр; проверка лимитов клавиатуры ловит неправильные раскладки до релиза.
- Vendor-пайплайн падает громко (неприменённый патч → исключение) — правильная позиция для строковых патчей.

### Проблемы

#### [High] Бесконечный цикл `ready↔cfg` в мосту iframe
`games/_boot.js:90` и `:93` шлют `ready` при загрузке **и** повторно внутри `start()`. Родитель отвечает `cfg` на *каждый* `ready` (`js/main.js:115`), а `_boot` вызывает `start()` на *каждый* `cfg` без гарда. Каждый `start()` добавляет новый `setInterval` (`:66`) → число поллинг-циклов и пар postMessage растёт бесконечно, CPU/память улетают при каждом открытии игры.
**Решение:** `ready` ровно один раз; `start()` с гардом `if (started) return;`; на стороне хаба дедуп окон.

#### [High] Аналитика молча дропается (неверный Content-Type)
`js/track.js:43-48` шлёт JSON-строку без `application/json` (`sendBeacon` → `text/plain`; `fetch` без заголовка). Fastify не парсит → `req.body` пуст → `isAction('')` ложь → `400`. **Все события хаба** (`open_game`, `finish`, `share_*`, `duel_*`) отклоняются; выживают только события бота (пишут в БД напрямую). `/stats` «слеп» по геймплею.
**Решение:** `Blob([body], {type:'application/json'})` для beacon + `headers:{'Content-Type':'application/json'}` для fetch; опционально парсер `text/plain` на сервере в запас.

#### [Medium] Daily-seed зависит от локального часового пояса
`js/main.js:48-53` берёт `getFullYear/getMonth/getDate` устройства. Пользователи в разных часовых поясах (или с кривым временем) получают разный `?seed` → разный «пазл дня». Комментарий «один для всех за сутки» верен только внутри одного пояса.
**Решение:** якорить день к фиксированной зоне (Москва, `Europe/Moscow`).

#### [Medium] JSON-бэкенд теряет данные при запуске server+bot отдельными процессами
`server/db.mjs:64-72` — каждый процесс держит свой `jsonDb` и `saveJson()` перезаписывает весь файл. Совместное использование **файла** не есть общee состояние.
**Решение:** задокументировать JSON как single-process dev-only; требовать Postgres при совместном запуске; либо append-only JSONL.

#### [Medium] Хрупкий vendor-патчинг (строковые замены `Math.random`)
`tools/vendor.mjs` — ~50 точных многострочных замен, привязанных к форматированию апстрима. Любое реформатирование ломает патч. Daily-детерминизм разбросан (`Math.random`→`__hubRand` в sapper/quiz).
**Решение (высоколевередж):** вместо разбросанных замен — один seeded-PRNG shim, инжектящийся *перед* `script.js` игры: при наличии `?seed` делаем `Math.random = __hubSeeded`. Все игры становятся детерминированными равномерно, ~30 хрупких правок уходят. Остаёмся no-build.

#### [Low] Пробелы в тестах / нет lint / CI
Нет e2e теста postMessage-контракта (`_boot`↔`bridge`↔`onMessage`) — этим прошёл цикл `ready`. Не покрыты `parseStartParam`, `dailySeed` (таймзона), гейтинг консента, `/cast` (только ветка «нет текста»). Нет ESLint/Prettier, нет `.github/`.
**Решение:** добавить симуляцию обмена iframe↔hub; юнит-тесты `parseStartParam`/`dailySeed`/`consent`; минимальный GitHub Actions на `npm run smoke`.

## 2. Безопасность и 152-ФЗ

### Вердикт: NON-COMPLIANT (для публичного запуска как есть)

Ключевой разрыв: **идентификатор (`user_id`) собирается и передаётся в аналитику *до* получения согласия и в *сыром* (не хешированном) виде.** 152-ФЗ (ст. 6, 9) требует явного согласия *до* сбора/обработки ПД. Компенсирующий ре-хеш на сервере спасает at-rest, но сырые ПД всё равно уходят с клиента.

### Сильные стороны
- Сервер ре-хеширует не-32-hex значения (`server/index.mjs:49-51`) — store никогда не хранит сырой id.
- `/forget` корректно проведён на стороне бота (`bot/bot.mjs:136-139`) через аутентифицированный `ctx.user.user_id`.
- `parseStartParam` строго валидирован регэкспом (`js/main.js:39-45`); `onMessage` проверяет `e.source` и тег `__hub` — нет подмены счёта извне.
- Секреты чисты: только `.env.example`; реальный `.env` в `.gitignore`; бот не стартует без `BOT_TOKEN`.

### Критические

#### [Critical] Сырой `user_id` шлётся как `uid_hash` — комментарий сервера ложен
`js/track.js:28` кладёт сырой `initDataUnsafe.user.id` в поле `uid_hash`. Комментарий «хаб шлёт уже хешированный» (`server/index.mjs:47-48`) **неверен** — клиент не хеширует. Сырой ПД уходит по сети (в cleartext при `http://`).
**Решение:** хешировать в браузере *до* сборки пейлоада; поправить комментарий. Серверный ре-хеш оставить как defence-in-depth.

#### [Critical] События аналитики несут идентификатор БЕЗ согласия
`js/track.js:26-52` шлёт `uid_hash` на *каждом* событии, включая первый `open_bot` (`js/main.js:235`) **до** показа диалога согласия. `hasConsent()` (`:34`) записывается лишь как поле `consent:` и не блокирует передачу. Прямое нарушение 152-ФЗ; `legal/POLICY.md` обещает обратное.
**Решение:** гейтить `track()` по консенту; до `setConsent()` слать `uid_hash:'anon'`.

#### [Critical] `/forget` не аутентифицирован и не авторизован
`server/index.mjs:78-83` — любой (CORS `*`, без токена) может POST `{user_id:N}` и стереть подписчика и все его события. Перебором числовых ID стирается вся база подписчиков (единственный канал связи оператора).
**Решение:** не выставлять публичный delete-by-id; эрэйжер только через подписанную bot-команду (или верифицированный `initData` HMAC). Rate-limit.

#### [Critical] Админ-чек fail-open: при пустом `ADMIN_IDS` админ — все
`bot/bot.mjs:14` `isAdmin = (uid) => !ADMIN_IDS.length || ADMIN_IDS.includes(...)`. С дефолтным (не заданным) `HUB_ADMIN_IDS` (`bot/config.mjs:47-48`) `ADMIN_IDS=[]` ⇒ `isAdmin` true для каждого ⇒ `/cast` (рассылка всем) и `/stats` открыты любому юзеру MAX.
**Решение:** fail-closed: `ADMIN_IDS.length>0 && ADMIN_IDS.includes(...)`; отказывать в `/cast`/`/stats` при пустом списке.

### Высокие

- **[High] `/sub` и `/ev` без аутентификации, CORS `*`, нет rate-limit** (`server/index.mjs:32-76`): спам/DoS аналитики; сайт жертвы может подписать чужие ID (рассылка несогласным). Пропущенный `consent` трактуется как `true`.
  → ограничить CORS до хаб-ориджина; rate-limit; требовать подписанный `initData` для `/sub`; missing consent = `false`.
- **[High] `HUB_HASH_SALT` по умолчанию `'change-me-in-production'`** (`server/db.mjs:20`): псевдообезличивание сломано, хеши перебираемы. → генерировать длинную случайную соль при деплое; отказывать в старте на дефолте; хранить в секрет-менеджере.
- **[High] JSON-бэкенд пишет сырой `user_id` в `server/data.json` в открытом виде, файл не в `.gitignore`** (`server/db.mjs:21,99`): риск коммита ПД в VCS (репорт-абл инцидент). → добавить `server/data.json` в `.gitignore`; шифровать или мигрировать на Postgres.
- **[High] Сервер на HTTP, bind `0.0.0.0`** (`server/index.mjs:105`): при `HUB_TRACK_ENDPOINT=http://` сырой `user_id` в cleartext (нарушение шифрования транзита 152-ФЗ). → TLS-терминация, требовать `https://`.

### Средние / низкие
- **[Medium] JSON-запись не атомарна** (`db.mjs:69-71` `writeFileSync` целиком) → риск повреждения при краше. → tmp+rename или Postgres.
- **[Low] `postMessage` в `_boot.js` не проверяет origin** (`:34-39`): low-риск (same-origin, только конфиг), но стоит валидировать `e.origin`/`source`.
- **[Low] XSS не найдено**: все `innerHTML` — статический/операторский контент; `score`/`challenge` — числа через `textContent`; `parseStartParam` безопасен. Держать `innerHTML` только для доверенного конфига.

### Must-fix перед публичным запуском (чек-лист)
1. Консент ДО того, как идентификатор покинет клиент (`track()` анонимен до `setConsent()`).
2. Реально хешировать `user_id` в браузере + поправить ложный комментарий.
3. Закрыть админ: fail-closed `isAdmin`, отказ `/cast`/`/stats` при пустом `ADMIN_IDS`.
4. Аутентифицировать `/forget` (только bot-команда / подписанный initData).
5. Защитить `/sub` и `/ev`: CORS по ориджину, rate-limit, signed initData, missing consent=false.
6. Реальный `HUB_HASH_SALT` (отказ старта на дефолте).
7. `.gitignore` для `server/data.json`; не хранить сырые ПД в открытом виде.
8. HTTPS/TLS для всего; `https://` endpoint.
9. Атомарные JSON-записи или Postgres.
10. Привести `legal/POLICY.md` в соответствие с кодом; подписать у 152-ФЗ-специалиста.

- Исправить цикл `ready↔cfg` в мосту (`_boot.js` + `main.js`).
- Исправить Content-Type аналитики (`track.js` → `application/json`).
