# События и воронка

## Что отправляется

Браузерная аналитика идёт на `window.HUB_TRACK_ENDPOINT`. В production-топологии это
`/hub-api/ev` — тот же origin, что и оболочка (см. `deploy/Caddyfile.hub`). Поэтому
события не требуют CORS и разрешаются CSP через `connect-src 'self'`.

Если server не запущен или endpoint неверный, браузер отправляет beacon в 502, и
события теряются **молча** — в server logs не будет ни одной записи. Проверяйте
доступность `/hub-api/health` и непустой `verified_events` в `/stats` после выкладки.

Допустимые значения endpoint: same-origin относительный путь (`/hub-api/ev`) либо
абсолютный HTTPS URL. `http://` endpoint на `https://` странице отбрасывается на
стороне клиента, чтобы не получать потерю событий без диагностики.

## Достоверность воронки

`funnel` и `game_funnel` считаются **только по событиям с валидной подписью MAX
`initData`**. Остальные события сохраняются, но в KPI не попадают.

Причина: `/ev` — публичный POST. Без проверки подписи любой HTTP-клиент отправил бы
`open_bot` / `open_game` / `finish` с произвольным `sid` и задал `start_rate_pct`,
`completion_rate_pct` и `game_funnel` вручную — то есть решения §7 принимались бы по
подделанным данным. Rate limiting на ingress ограничивает масштаб, но не делает данные
достоверными.

События бота помечаются `verified: true`: они приходят через webhook,
аутентифицированный `HUB_BOT_WEBHOOK_SECRET`, то есть источник достоверен на стороне
сервера.

## Счётчики доверия

В ответе `/stats`:

| Поле | Значение |
| --- | --- |
| `verified_events` | подписанные события, попавшие в воронку |
| `unverified_events` | неподписанные события (сохранены, но не в KPI) |
| `verified_share_pct` | доля подписанных событий в окне |

`verified_share_pct` нельзя читать как «доля валидных пользователей». Клиент намеренно
не отправляет signed `initData` до согласия — требование 152-ФЗ (`legal/POLICY.md` §3),
поэтому pre-consent трафик неподписан по построению, и значение будет заметно ниже
100%. Это ожидаемо.

Низкое `verified_share_pct` означает, что воронка построена на небольшой подписанной
выборке: решения по ней нужно принимать осторожно, а `unverified_events` — мониторить
как признак шума или неверно настроенного endpoint.

§4 Minimum sample применяется к `verified_events`: продуктовое решение не принимается,
пока подписанной выборки мало, даже если `open_sessions` много.

## Схема

Колонка `hub_events.verified` добавлена аддитивно:
`ADD COLUMN IF NOT EXISTS verified boolean NOT NULL DEFAULT false`. Существующие строки
получают `false` и выходят из воронки, а не начинают молча учитываться, — это
безопасное направление для доверия к KPI.

## Миграция

DDL выполняется автоматически при старте `server` и `bot`
(`CREATE TABLE IF NOT EXISTS` + `ADD COLUMN IF NOT EXISTS`). Отдельный шаг миграции не
требуется, откат — предыдущий SHA: лишняя колонка не мешает старой версии кода.
